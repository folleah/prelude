## Context

`planning-prompt.md` задаёт правила выбора по слоям. Запрос уже включает описание, ответы discovery, текущий YAML, признаки репозитория, обнаруженные инструменты, индекс скиллов и пользовательские приоритеты. `prelude-format.md` задаёт контракт ответа, а приложение проверяет и применяет операции. Этого контекста достаточно для первой итерации.

## Goals / Non-Goals

**Goals**

- Получать связный план, по которому агент может выполнить первую задачу и проверить результат.
- Сравнивать качество по заранее заданным признакам на одинаковых входах.

**Non-Goals**

- Отдельные планировщики для платформ, парсеры менеджеров пакетов, новые механизмы исполнения хуков и изменения формата проекта.

## Decisions

1. В едином системном промпте задать порядок решений. Сначала выделить сценарии, компоненты и ограничения, затем первую проверяемую задачу и зависимости между рабочими потоками, потом подобрать модули и проверки. Перед ответом сверить план со вводными пользователя. Один алгоритм применим и к проекту с несколькими платформами.
2. Сохранять доказательность. При точечном изменении учитывать текущий YAML и исходные инструкции. Использовать явные требования, обнаруженные факты и каталог как основания решений. Неизвестное отражать как допущение или шаг настройки. Выбор ролей, скиллов и текста хуков оставлять модели. Для обычной разработки проверять готовность начать работу с чистого репозитория, включая зависимости, запуск и применимые проверки.
3. Использовать существующие поля для результата. Проектный контекст записывать в `projectBrief`, рабочий порядок и согласования — в роли и инструкции, применимые быстрые действия — в `hookChecks`. Проверки с реальными внешними сервисами, устройствами или длительными прогонами описывать отдельно с условием запуска. При отсутствии подтверждённой команды указывать действие и необходимость настройки. Дополнительный запрос к модели для внутренней проверки плана не требуется.
4. Сравнивать результаты по задачам, а не по точному набору продуктов или формулировок. Записать базовую версию промпта и повторить те же сценарии с теми же моделью, параметрами, входным контекстом и снимком каталога. Проверять сохранность требований, осуществимость первой задачи, обоснование выбора модулей, независимость ролей и пригодность проверок. Для точечной правки дополнительно проверять сохранение остального плана.

## Risks / Trade-offs

- Модель может формально заполнить все слои и предложить лишнее. Оценивать каждую роль, модуль и проверку по связи с задачей.
- Снимок каталога может не содержать нужного инструмента. Использовать доступные средства поиска и фиксировать недостающий инструмент в инструкциях, когда подходящего ID нет.
- Работа модели вариативна. Хранить условия прогона и конкретные примеры результатов. При отсутствии доступа к модели фиксировать блокировку сравнения отдельно от локальной проверки формата.

## Migration Plan

Обновление применяется при следующем планировании. Текущие планы, история и экспорт продолжают использовать существующую схему. Для отката достаточно вернуть предыдущую версию системных инструкций.
