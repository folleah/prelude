# environment-planning Specification

## Purpose

Подбор и проверка окружения агентной разработки с учётом проекта, доступных моделей и бюджета.

## Requirements

### Requirement: Входные данные
Приложение SHALL принимать описание идеи или признаки выбранного репозитория, бюджет, приоритет и доступ к выбранному провайдеру. Локальные признаки SHALL извлекаться без выполнения кода проекта.

#### Scenario: Проект по описанию
- **WHEN** пользователь начинает обсуждение нового проекта
- **THEN** Prelude уточняет вопросы, влияющие на окружение, и передаёт ответы при формировании плана

#### Scenario: Проект без репозитория
- **WHEN** пользователь вводит идею
- **THEN** приложение задаёт необходимые уточнения, затем запрашивает план с рекомендациями и допущениями

#### Scenario: Локальный репозиторий
- **WHEN** пользователь выбирает каталог
- **THEN** приложение извлекает признаки проекта без выполнения его кода или изменения файлов

### Requirement: Расширяемый каталог
Приложение SHALL читать локальные YAML/JSON-записи с типом, источником, зависимостями, конфликтами и сведениями о совместимости. Каталог SHALL описывать назначение, категории и способ подключения модулей, включая инструменты компактизации контекста и построения графа проекта. Начальный каталог SHALL включать Codex, Claude Code, OpenCode и записи Graphify, Ponytail, OmniRoute и OpenSpec.

#### Scenario: Дополнение каталога
- **WHEN** пользователь добавляет корректную запись с уникальным идентификатором
- **THEN** она становится доступна ИИ при следующем формировании запроса

#### Scenario: Повреждённая запись
- **WHEN** файл содержит неизвестную версию схемы или дублирующий идентификатор
- **THEN** приложение показывает источник ошибки и исключает недействительное расширение

### Requirement: Рекомендации и бюджет
ИИ SHALL рекомендовать harness, роли, модели, правила взаимодействия и инструменты с обоснованием выбора. Приложение SHALL проверять ссылки на каталог и учитывать бюджет, приоритет и неопределённость стоимости при оценке окружения.

#### Scenario: Выбор модели по умолчанию
- **WHEN** пользователь не указал конкретную модель для проекта
- **THEN** план учитывает совместимость и предпочитает высококачественную доступную модель с учётом ограничений

#### Scenario: Экономия
- **WHEN** при заданном бюджете есть совместимые варианты с разной стоимостью
- **THEN** запрос к ИИ передаёт известные квоты и локальные модели и требует предпочесть меньшие расходы при прочих равных

#### Scenario: Недостаточно данных
- **WHEN** стоимость или доступная квота неизвестна
- **THEN** оценка оставляет сведения неопределёнными

#### Scenario: Малый проект
- **WHEN** одна роль покрывает задачи проекта
- **THEN** план ИИ предлагает одну роль и содержит уникальные инструкции

### Requirement: Редактирование и совместимость
Приложение SHALL принимать изменения компонентов, ролей и инструкций через чат и проверять их локально на зависимости, конфликты и совместимость. Неразрешённые блокирующие проблемы SHALL препятствовать выдаче конфигурации.

#### Scenario: Изменение плана через чат
- **WHEN** пользователь просит добавить или убрать модуль
- **THEN** Prelude применяет только проверенные операции и показывает обновлённую схему

#### Scenario: Несовместимое изменение
- **WHEN** операция модели оставляет компонент с неудовлетворённой зависимостью
- **THEN** Prelude отклоняет изменения и показывает причину в чате

### Requirement: Конструктор и тарифы
Конструктор SHALL показывать состав окружения и сведения о выбранном модуле. Для модели OpenRouter при подключении интерфейс SHALL показывать известные ставки за входной и выходной токен или сообщать, что ставки недоступны.

#### Scenario: Настройка OpenRouter
- **WHEN** пользователь выбирает модель OpenRouter
- **THEN** Prelude показывает доступные ставки в блоке подключения и сохраняет канвас для работы со схемой

#### Scenario: Замена модели
- **WHEN** пользователь выбирает другую модель OpenRouter
- **THEN** блок подключения показывает ставки выбранной модели, когда они известны

### Requirement: Обмен планом с ИИ
Prelude SHALL поддерживать подключение ChatGPT и API-ключом через совместимый HTTPS endpoint. Модель для чата SHALL выбираться из списка, а при подключении по ключу SHALL допускаться необязательный ID модели. Планирование SHALL использовать выбранного провайдера с операцией чтения каталога и локальной проверкой результата.

#### Scenario: Подключение и запрос плана
- **WHEN** пользователь подключает провайдера и отправляет сообщение
- **THEN** Prelude выполняет запрос из приложения и обновляет план после проверки результата

#### Scenario: Успешное получение плана
- **WHEN** пользователь отправляет запрос после подключения ChatGPT и модель возвращает корректные операции
- **THEN** Prelude обновляет конструктор и оставляет чат доступным для дальнейших изменений

#### Scenario: Подключение по API-ключу
- **WHEN** пользователь подключает совместимый HTTPS endpoint с API-ключом и выбирает модель
- **THEN** Prelude выполняет планирование с доступом модели к каталогу

#### Scenario: Настройки подключения
- **WHEN** пользователь открывает настройки подключения
- **THEN** Prelude показывает статус и действия для активного способа входа и маскирует ключ API

#### Scenario: Неизвестный модуль или повреждённый ответ
- **WHEN** проверка отклоняет неизвестный идентификатор или формат остаётся некорректным после автоматических попыток
- **THEN** Prelude сохраняет текущую схему и сообщает о проблеме в чате

### Requirement: Сохранённая авторизация и выход
Prelude SHALL восстанавливать сохранённое подключение при запуске. Кнопка выхода под настройками SHALL очищать сохранённые сессии ChatGPT и API-провайдера и возвращать на экран авторизации после успешной очистки.

#### Scenario: Выход при нескольких сохранённых сессиях
- **WHEN** пользователь нажимает Выход
- **THEN** следующий запуск требует подключения, даже если ранее были сохранены данные двух провайдеров

### Requirement: Браузерный вход ChatGPT
Prelude SHALL завершать браузерную авторизацию через локальный callback с проверкой состояния и показывать результат в приложении. Сетевой клиент SHALL учитывать поддерживаемые настройки прокси Windows.

#### Scenario: Ответ браузера
- **WHEN** пользователь завершает вход через браузер
- **THEN** Prelude обрабатывает результат callback и обновляет состояние подключения либо показывает ошибку провайдера

### Requirement: Пошаговое уточнение проекта
Discovery SHALL запрашивать до трёх коротких вопросов в виде обычного текста и показывать их по одному. При достаточном описании SHALL допускаться переход непосредственно к планированию.

#### Scenario: Не хватает архитектурного решения
- **WHEN** из описания непонятно, нужен ли блогу редактор с хранилищем
- **THEN** чат задаёт первый вопрос и показывает следующий после ответа

### Requirement: Чат и состояние запроса
Prelude SHALL сразу отображать отправленное сообщение и индикатор ожидания. Enter SHALL отправлять сообщение, а Shift+Enter и Alt+Enter SHALL вставлять перевод строки. История SHALL сохраняться вместе с проектом.

#### Scenario: Ответ провайдера с ошибкой
- **WHEN** провайдер возвращает ошибку с текстом
- **THEN** чат показывает сообщение об ошибке с доступными деталями

### Requirement: YAML-операции и восстановление формата
Планировщик SHALL передавать модели текущую схему и описание формата и получать операции как YAML. При ошибке разбора формата Discovery или плана приложение SHALL запрашивать исправление до двух раз.

#### Scenario: Успешное восстановление
- **WHEN** модель исправляет формат в допустимое число попыток
- **THEN** Prelude использует исправленный ответ без сообщения о первой ошибке

### Requirement: Канвас конструктора
Канвас SHALL показывать вертикально упорядоченные слои, включая пустые, и размещать карточки по горизонтали с центрированием. Изменения SHALL выполняться через чат. Выбор карточки SHALL открывать детали справа, а нажатие в пустой области SHALL сбрасывать выбор.

#### Scenario: Просмотр карточки
- **WHEN** пользователь выбирает модуль
- **THEN** инспектор показывает его назначение, известную версию и ссылку на источник при наличии

### Requirement: Независимая прокрутка
Конструктор SHALL занимать высоту окна. Поле ввода и селектор модели SHALL оставаться внизу панели чата. История чата, канвас и детали SHALL прокручиваться в собственных областях при переполнении.

#### Scenario: Длинная переписка
- **WHEN** история превышает доступную высоту
- **THEN** пользователь прокручивает сообщения, сохраняя доступ к полю ввода

### Requirement: Параллельные роли
План SHALL указывать параллельность только для независимых ролей. При наличии параллельных ролей Prelude SHALL предлагать подходящие менеджеры сессий с учётом платформы и обнаруженных инструментов.

#### Scenario: Две параллельные роли
- **WHEN** две роли отмечены как способные работать одновременно
- **THEN** конструктор показывает рекомендацию инструментов управления сессиями

### Requirement: Полнота инфраструктуры
Начальный план SHALL учитывать версионирование, зависимости, локальный запуск, проверки и сборку. Для программного проекта по умолчанию SHALL предусматриваться Git, а для нового веб-проекта TypeScript SHALL дополняться подходящим runtime, менеджером пакетов и сборкой. Существующий lockfile и явные предпочтения SHALL учитываться.

#### Scenario: TypeScript-веб-проект
- **WHEN** пользователь задаёт TypeScript без остальных инструментов
- **THEN** Prelude предлагает полный применимый стек и описывает команды и зависимости

### Requirement: Локально доступные инструменты
Prelude SHALL определять доступность поддерживаемых команд через PATH без запуска этих команд и передавать результат планировщику. Правила начального плана SHALL учитывать установленный Docker для программных проектов и ограничения пользователя.

#### Scenario: Docker доступен
- **WHEN** создаётся план программного проекта и Docker найден
- **THEN** модель получает сигнал о доступности и правило выбора Docker с учётом ограничений

### Requirement: Рекомендации по скиллам
Планировщик SHALL получать текущий индекс активных скиллов, включая встроенные и локально закэшированные. При подборе SHALL учитываться назначение, совместимость, бесплатность и правила для текста, веб-интерфейсов и оптимизации контекста.

#### Scenario: Сайт с публичными текстами
- **WHEN** проект включает тексты для посетителей и веб-интерфейс
- **THEN** модель получает инструкции рассмотреть Humanizer и подходящие рекомендации по веб-дизайну

### Requirement: Поиск скиллов по запросу
Планировщик SHALL иметь возможность отправить короткий тематический запрос к публичному поиску skills.sh, проверить наличие соответствующего SKILL.md в ревизии GitHub и использовать число установок как сигнал популярности. Выбранные найденные скиллы SHALL сохраняться в локальном каталоге.

#### Scenario: Пробел в локальном каталоге
- **WHEN** модель запрашивает конкретный тип скилла
- **THEN** Prelude передаёт проверенные результаты, а при сбое возвращает локальный каталог

### Requirement: Фоновый каталог скиллов
Prelude SHALL поддерживать локальный кэш метаданных скиллов из настроенных источников и автоматическую проверку при запуске с суточным интервалом. Архивные записи SHALL исключаться из новых рекомендаций. Глобальная панель SHALL исключать отдельный пункт Skills.

#### Scenario: Запуск после обновления каталога
- **WHEN** локальный кэш уже загружен
- **THEN** планировщик может использовать актуальные записи из кэша
